# The 68000 recompiler

How the Classic 2D cores run their 68000 programs: the static recompiler
(`tools/m68krecomp`), the timing model that makes its code behave like
MAME's 68000 down to the bus cycle, the fallback interpreter for code the
recompiler did not reach, and the Musashi mode for the Y Board. The boards
around it are in [CLASSIC2D.md](CLASSIC2D.md).

## Purpose and scope

Every Classic 2D board except System 32 has two or three 68000s, often
sharing RAM and talking through latches. The cores must match MAME's traces
instruction by instruction across all of them, so the 68000 has to do more
than run the right instructions. It has to make each memory access at the
same moment MAME's 68000 does, relative to the other CPUs and the timers.

In scope:

- translating a 68000 program into C++ ahead of time, including the FD1094
  and FD1089 encrypted programs;
- MAME's cycle-exact 68000 timing (`m68000.cpp`) for the Hang-On board, the
  Out Run board and the X Board;
- Musashi's timing (`m68kcpu.cpp`) for the Y Board, which MAME runs on
  Musashi;
- running code the recompiler never saw, with the same timing.

## Requirements

1. The generated code runs whole instructions, in plain C++ with no
   microcode engine, so it stays fast and portable.
2. Every instruction takes MAME's number of cycles, samples its interrupt
   lines where MAME does, and makes each device or shared-RAM access at
   MAME's bus cycle, even when the instruction crosses a timeslice's end.
3. The recompiled code and the interpreter give identical results, so a
   game can move between them at any instruction.
4. No ROM bytes in the repository: the recompiler reads the user's program
   image at build time, and only addresses (seeds) are committed.

## Design

### Translating a program

`m68krecomp IMAGE OUT.cpp --ns NAME --seeds FILE [--pointers --scan]
[--opcodes OPIMAGE] [--musashi]`

1. **Find the code.** The search starts from the reset and exception
   vectors and from the seeds: every address MAME executed in the attract,
   test and game runs (`ORTRACE_PCS`). It follows branches and calls and
   adds what it can prove (`src/m68k/reach.cpp`):
   - jump tables (`lea TABLE,An` then `jmp (An,Dn.w)`, PC-relative tables,
     word offset tables read before the jump);
   - handler pointers: `move.l #addr`, `lea addr` and longwords in data that
     point at code. Each candidate is kept only if everything reachable from
     it decodes cleanly and does not cut through code already found.
2. **Decode.** `src/m68k/decode.cpp` turns each instruction into a
   structure: operation, size, effective addresses, extension words.
3. **Emit.** Each instruction becomes a block of C++ that updates the CPU
   state (`m68k::Cpu`: registers, flags, cycle count, instruction count),
   with a dispatch switch on the program counter. A jump to an address the
   program has no code for calls `Env::missing`, which hands over to the
   interpreter.

Out Run shows what discovery adds. Without the MAME seeds, discovery alone
reaches 8,009 of the 8,045 main CPU addresses and all 1,020 sub CPU
addresses that MAME executed. With the seeds, the main program has 11,965
instructions.

### Encrypted programs

- **FD1094** (Turbo Out Run, Thunder Blade and several X Board sets). Only
  opcode fetches are decrypted, and the key state changes as the program
  runs. The recompiler reads two images: the raw ROM for data
  (`<set>_main.bin`) and an opcode image (`--opcodes <set>_main_op.bin`) in
  which each word is decrypted in the state the CPU fetches it in. The
  states come from MAME's runs (the seeds carry "PC STATE"). A word no run
  executed takes the state of the nearest executed word before it. The
  reset vectors are a decrypted fetch in state 0. The recompiler writes the
  states into its output, so the board rebuilds the same opcode image at
  load time for the interpreter.
- **FD1089** (Enduro Racer). The key is fixed, so the whole program is
  decrypted up front into an opcode image and a data image. The reset
  vectors come from the opcode image.

### Timing: MAME's cycle-exact 68000

MAME's 68000 is a microcode engine. It can stop at any bus access when its
timeslice runs out, and it finishes the instruction in the next slice. The
generated code always finishes the instruction, so it reproduces what that
stop would change, one rule at a time:

- **Cycle counts.** `src/m68k/timing.h` holds MAME's cycle count for every
  instruction and addressing mode. It is one table, shared by the
  recompiler and the interpreter, and the recompiler checks every
  instruction it emits against it.
- **Overshoot is debt.** An instruction that ends past the slice's end
  carries the extra cycles into the next slice, as MAME carries its
  `m_count_before_instruction_step`.
- **Split before the first access.** An instruction whose first bus access
  would fall past the slice's end is not started: the slice ends before it
  and the cycles are a credit for the next one.
- **Access times.** Each instruction sets `c.late_r` and `c.late_w`: how
  many cycles before its end its reads and writes happen. Devices see the
  access at the instruction's end less `late`. Instructions with several
  accesses set it per access: MOVEP writes each byte 4 cycles apart, and
  MOVEM to memory writes each word on its own cycle (the first after the
  extension words, then one every 4 cycles, with -(An) writing each long's
  low word first).
- **Deferred writes.** A RAM or device write whose bus cycle starts at or
  after the slice's end is held (`Cpu::defer`) and made in the slice its
  cycle starts in. The other CPUs see the old value until then, as they do
  in MAME.
- **Reset in the gap.** If another CPU resets this one between such an
  instruction's stop point and its end, the instruction's register writes
  and held writes are thrown away (`save_da`/`restore_da`), because in MAME
  it never finished.
- **Interrupt sampling.** MAME samples the interrupt lines at a fixed bus
  cycle near each instruction's end (the access before the next opcode
  load). The generated code records that cycle (`c.ys`). A slice that ends
  between the sample and the instruction's end uses the old sample. Special
  cases, each found against MAME's traces:
  - MOVE to SR and ANDI, ORI or EORI to SR or CCR sample 4 cycles before
    their end.
  - DIVU/DIVS #imm sample after the immediate's fetch.
  - A read-modify-write whose write cuts a slice short has already sampled,
    so an interrupt raised meanwhile waits one more instruction.
- **Return to the board.** Instructions that change what interrupts can be
  taken (SR writes, RTE, TRAP, STOP) end the generated block so that
  `M68kExec` can check the lines, as MAME's execute loop does.

`orun::M68kExec` (`src/outrun/m68k_exec.cpp`) is the scheduler's view of the
CPU, as MAME's `m68000_device`: it runs the generated code to the slice's
target, takes interrupts through the board's interrupt mixer, and handles
RESET and HALT.

### Timing: Musashi on the Y Board

MAME's Y Board runs its three 68000s on Musashi, which is not cycle-exact.
With `m68krecomp --musashi`, set for every Y Board set, and
`orun::MusashiExec`:

- The cycle counts are Musashi's table (`src/m68k/musashi_cycles.h`,
  generated by `scripts/gen_musashi_cycles.py`; it matches the table MAME
  uses entry for entry), with Musashi's extra cycles for branches, MOVEM,
  TRAP and RESET.
- Every bus access happens at the instruction's start, with no dummy reads.
- Interrupts are taken when a slice starts and right after a status
  register write, at 44 cycles each.
- The flag rules for BCD, DIV overflow and CHK are Musashi's.
- **Address errors.** A word or long access at an odd address raises an
  address error with Musashi's stack frame and cost, and jumps to vector 3.
  Strike Fighter's X CPU relies on this. On the other boards an odd access
  still stops the core, because MAME's cycle-exact core would behave
  differently and no game needs it.

### The fallback interpreter

`m68k::Interp` (`src/cpu68k/interp.cpp`) runs code the recompiler did not
reach. It decodes with the recompiler's decoder and applies the same flag
helpers, cycle counts, split and defer rules, interrupt sampling and access
times, both cycle-exact and Musashi. It runs until control is back at an
address with recompiled code, the slice ends, or an instruction has to
return to the board. Code in ROM is decoded once and cached; code in RAM is
decoded each time.

Each new address the interpreter runs is logged once ("fallback interpreter
at ..."). The fix is to add it to the seeds, so the next build compiles it.

## Data and settings

The seeds (`seeds/<set>.main`, `.sub`, and `.subx`/`.suby` on the Y Board)
are the only per-set data. They are lists of addresses, with FD1094 states
where needed, merged from MAME's attract, test and game runs.

Two build switches help with debugging:

- `AF_DEBUG_C2D_INTERP=all` runs every instruction in the interpreter instead of the
  recompiled code.
- `ORUN_WATCH=OFFSET:FRAME` (trace tools) prints every change of a shared
  RAM word, checked at each instruction of both CPUs.

## Platforms

The generated code is plain C++ with no platform code, the same on every
target. Generated files are large, so builds compile at most two at once.

## Testing

- **Against MAME.** The board traces compare every CPU's registers every
  4096 instructions and every screen update ([CLASSIC2D.md](CLASSIC2D.md)).
  Every timing rule above was added because a trace diverged without it.
  Each rule was then checked on the other boards' sets, whose traces must
  stay identical.
- **Interpreter against recompiled.** With `AF_DEBUG_C2D_INTERP=all`, frame hashes
  and audio are identical to the recompiled build: outrun, thndrbld,
  aburner2 and shangon, 3000 to 6000 frames each with coin, start and play.
  Out Run recompiled from the vectors only, mostly interpreted with
  thousands of hand-overs each way, is also identical.
- **Emitted against the table.** The recompiler checks each instruction's
  emitted cycles against `src/m68k/timing.h` and fails the build if they
  differ.

## Open items

- A read past the slice's end after an instruction's first access is still
  made early. Only the first access is covered by the split rule. No game
  has shown a difference from it yet.
- The decoder, the recompiler and the timing tables move to Common, shared
  with the Model 2 cores' sound board 68000.

## Decisions

- **Whole instructions, not a microcode engine.** A microcode 68000 would
  match MAME by construction, but it would be several times slower and
  would not be recompiled code. Patching in MAME's access times reached
  the same traces on every board.
- **One timing table for both paths.** The interpreter and the recompiler
  read `timing.h`, so they cannot drift apart.
- **Musashi only where MAME uses it.** The Y Board gets Musashi's timing
  because MAME's Y Board uses Musashi. Using the cycle-exact rules there
  would never match the oracle.
- **Address errors only on Musashi boards.** They follow Musashi's
  behaviour exactly. Turning them on elsewhere would add code to every
  access for no game that needs it.
